## Как я понял задание

- Это дашборд-наблюдатель: входа и CRUD нет. Точки и товары заведены заранее.
- Пользователь меняет только три вещи: окно рейтинга, план на день, ответственного.
- Вся сложность под капотом: приём событий, идемпотентность, SQL-рейтинг, алерты.

## feature/backend-domain-design

- Моя идея была: один агрегат на всё, чтобы меньше кода. Codex возразил, я согласен.
- Агрегат это граница согласованности, а не папка. Один общий заставил бы пять симуляторов ждать друг друга.
- Остались два агрегата: SaleReceipt (защита от гонок при возвратах) и Outlet.
- Рейтинги, карточка точки, топ товаров это SQL-запросы (read models), не агрегаты.
- Упрощения под срок: один канал WebSocket (флаги stale и behind plan внутри строк рейтинга), без lease в outbox, без дневной динамики, настройки без версии (последняя запись побеждает), сумма возврата считается сервером, ранги уникальные (тай-брейк по outlet_id), рассылки объединяются раз в ~250 мс.
- Письма: at-least-once. После падения воркера возможен один дубль. Добавляю стабильный Message-ID честно пишу об этом.

## feature/events-ingestion

- Идемпотентность. В DynamoDB я делал через ConditionExpression. Здесь то же самое: PRIMARY KEY на event_id и INSERT ... ON CONFLICT DO NOTHING RETURNING.
- Строка вернулась: событие новое (201). Не вернулась: уже было, дальше сравнение хеша: тот же 200, другой 409.
- SELECT перед INSERT нельзя: между ними гонка.
- accepted_at задаётся приложением через Clock, а не базой: в тестах можно подставить время, повтор возвращает исходное значение. clock_timestamp() отличается от now() тем, что now() постоянен внутри транзакции.
- occurred_at храню отдельной колонкой для поиска поздних событий без разбора jsonb. Небольшое дублирование с canonical_payload, осознанно.
- Внешнего ключа на outlets пока нет, он появится после таблицы точек.
- Ответ на повтор собирается из колонок, а не хранится JSON.

- порядок в use case: проверить вход, посчитать хеш, вставить с ON CONFLICT, при конфликте сравнить хеш
- конфликт бросает исключение, чтобы откатить транзакцию целиком
- тест на десять параллельных запросов нужен, потому что простые тесты не ловят гонку

- добавлена валидация и ошибка на типизированная ошибка на валидацию
- тесты проходят идемпотичность повторных запросов
- конфликты событий возвращают нужную ошибку

- добавлены симуляторы и модели товаров
- создал еще таблицы отдельно для чеков и товаров со скидкой

- аонял, что bigint выбрасывает RangeError. Поэтому сначала проверяю количество через Number.isSafeInteger, иначе вместо ошибки 422 можно получить 500
- создал миграцию outlets и products. Добавил 5 точек с разными часовыми поясами IANA и 6 товаров с постоянными UUID

- разные часовые пояса не обязательно означают разные смещения UTC. Например, Алматы и Ташкент сейчас имеют одинаковое смещение
- еще нужно разобраться с приоритетом ошибок: если event_id уже существует, но новые данные содержат неизвестный товар, сейчас получаю 422 до проверки конфликта события.
- quantity переведён с PostgreSQL integer на bigint, теперь поддерживается весь диапазон Number.isSafeInteger
  до этого выползала ошибка что isSafeInteger допускает количество больше диапазона значению postgrsql инт

## feature/realtime-rankings

- решил рейтинг считать через sql, а не хранить отдельно готовые цифры, иначе пришлось бы постоянно следить чтобы данные совпадали
- немного разобрался с оконными функциями postgresql, через них можно выдавать места точкам
- если у двух точек одинаковая выручка нужен еще один критерий сортировки, для этого оставил outlet_id
- рейтинг зависит от выбранного окна, час день и так далее, поэтому нельзя просто суммировать все продажи
- websocket нужен чтобы фронт получал изменения без постоянных запросов к серверу
- столкнулся с тем что рейтинг может поменяться даже если новых продаж нет, просто старые продажи вышли из временного окна
- поэтому добавил обновление по таймеру, а не только при новых событиях
- проверил что данные через socket совпадают с обычным GET запросом

## feature/simulator

- создал отдельный симулятор для пяти точек, чтобы проверить как backend ведет себя с реальными параллельными запросами
- сначала просто генерировал продажи, потом добавил разные скорости для каждой точки
- добавил небольшую случайность по времени чтобы все запросы не приходили одновременно
- с ретраями был важный момент, нельзя каждый раз создавать новый event_id, иначе сервер посчитает это новой продажей
- поэтому тело запроса создается один раз и при ошибке отправляется повторно без изменений
- добавил имитацию отключения интернета, продажи в этот момент не теряются а складываются в очередь
- когда связь появляется отправляю накопленные продажи по порядку
- occurred_at при этом не меняется, потому что продажа произошла раньше а отправилась только сейчас
- из за ограничений по зависимостям пришлось отдельно прописать типы node в node.d.ts, обычно поставил бы @types/node
- во время проверки отправил продажи с пяти точек, количество записей в базе совпало с количеством созданных продаж
- было 35 поздних событий и 11 повторов, все обработалось правильно
- проверил последний снимок socket и GET рейтинга, цифры совпали

## feature/return-ingestion

- перешел к возвратам, тут оказалось немного сложнее чем с обычными продажами
- нужно проверять не только сам event_id но и сколько товара уже вернули по конкретному чеку
- если купили 3 товара нельзя потом двумя параллельными запросами вернуть по 3 каждый
- для этого блокирую чек через SELECT FOR UPDATE пока выполняется возврат
- сумму возврата считаю на сервере, потому что клиенту доверять ее нельзя
- цену беру из оригинального чека, даже если цена товара потом поменялась
- добавил частичные возвраты, чтобы можно было сначала вернуть одну штуку а потом остальные
- проверял чтобы при ошибке весь возврат откатывался, а не оставлял половину записанных изменений

## feature/outlet-details

- начал делать отдельную карточку точки, чтобы можно было посмотреть ее статистику
- сначала думал просто брать все продажи и считать в коде, но через sql получается проще
- для этого использовал read models которые уже обсуждали при проектировании архитектуры
- отдельно считаются данные по товарам, продажам и возвратам
- важно чтобы в карточке и общем рейтинге цифры не расходились
- денежные значения так же оставил строками, чтобы не терять точность на фронте

## feature/outlet-settings

- сделал изменение дневного плана и ответственного за точку
- тут логика намного проще чем с продажами, обычное обновление данных
- решил не добавлять версии настроек, последнее изменение просто перезаписывает предыдущее
- проверяю входные данные, чтобы например отрицательный план не попал в базу
- изменение плана потом влияет на проверку отставания точки, поэтому важно чтобы все брали актуальные данные из базы

## feature/stale-alerts

- добавил проверку точек которые долго не отправляют продажи
- сначала тут важно было разобраться какое именно время использовать
- occurred_at это когда продажа произошла, accepted_at это когда сервер ее принял
- для проверки активности использую last_accepted_at, потому что продажи могут приходить с опозданием
- если отправить старую продажу после отключения интернета, она все равно считается новой принятой записью
- при этом обычный повтор события не должен обновлять активность точки
- если точка еще ничего не продавала, нужно смотреть на activated_at
- еще понял что точка может стать неактивной просто со временем, даже если новых запросов вообще нет

## feature/midday-alerts

- добавил проверку точек которые к полудню не выполняют нужную часть дневного плана
- тут снова столкнулся с часовыми поясами, нельзя проверять все точки по времени Бишкека
- у каждой точки свой time_zone, поэтому полдень и начало дня нужно считать отдельно
- особенно интересно с Берлином, потому что там есть переход на летнее и зимнее время
- обычный UTC offset для такой логики не подходит, поэтому использую IANA зоны
- проверка опирается на текущую выручку и дневной план точки
- старался не писать отдельную формулу расчета продаж, а использовать ту же логику что уже есть в рейтинге

## feature/alert-email

- перешел к отправке писем при алертах
- для локальной проверки использую mailpit, письма можно смотреть без реальной отправки
- разобрался с outbox, смысл в том чтобы сначала сохранить уведомление в базе а потом уже пытаться отправить письмо
- иначе если приложение упадет между этими действиями уведомление просто потеряется
- добавил отдельную обработку очереди писем
- есть нюанс с at-least-once, если письмо отправилось а сервер упал до сохранения результата, при следующем запуске оно может отправиться повторно
- полностью убрать такую ситуацию без дополнительных механизмов сложно, поэтому пока оставил это ограничение
- использую стабильный Message-ID чтобы одинаковые письма можно было распознать
- проверял отправку через mailpit и тесты
